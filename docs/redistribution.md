This document records the source/artifact evidence required to accompany release binaries. It is not legal advice, a legal-approval statement, or a determination that a particular binary is cleared for redistribution. The platform manifests deliberately keep `publicReleaseReady` false where evidence is incomplete:

- `../packaging/provenance/linux-runtime.json` — observed Linux release tree, pinned input, recipe, hashes, notices, and unresolved mappings.

## LGPL replacement and delivery scope

The LGPL-3.0 text requires corresponding source for the LGPL-covered library, including modifications and the scripts needed to control compilation and installation, but it does not make exact toolchain/container image digests, byte-for-byte reproducibility, or reproducible-build certification a general legal prerequisite. Those details can be valuable technical evidence and may be necessary to explain or reproduce a particular build; they must not be conflated with the LGPL's source and replacement conditions.

For an LGPL-covered library used through a suitable shared-library mechanism, the distributor must allow replacement with a modified compatible library and not impose restrictions that prevent exercising that right; the applicable LGPL terms also address reverse engineering for debugging modifications. Installation information is relevant when the work is conveyed in or for a User Product within GPLv3's definition and the conditions there apply; it is not a blanket requirement for every ordinary desktop distribution. Assess the actual product/distribution and the selected LGPL version rather than asserting either automatic applicability or automatic exemption. In particular, the shipped Windows Qt DLLs and Linux Qt shared libraries are dynamically loaded, but package evidence alone does not establish all replacement, source, notice, or installation-information conditions.

A practical distributor-controlled route for a future release is a versioned companion corresponding-source archive offered alongside each exact binary release, with immutable digests and a retained copy for the required term. That archive can include the exact source, modifications, applicable license/notice texts, and required scripts; a release URL must remain under distributor control and actually serve the bundle. The retained Qt and mpv files are not yet that complete bundle, and nothing here claims a source offer has been published. Do not use external upstream links or binary SDKs as substitutes for a distributor-controlled offer.

## Combined practical source fulfillment

Prepare one release-specific source bundle for the exact Windows and Linux artifacts. Keep each binary's hash and package path associated with the corresponding component record; keep both source trees separate where they differ. Include, as applicable:

1. Exact corresponding upstream sources (including generated or vendored sources and submodules), version/revision, and the source archive's own digest.
2. Every patch, modification, configuration option, compiler/linker command, dependency source and build/install script used to produce or postprocess the shipped binary. Include the Qt deployment steps and the Linux `$ORIGIN` RUNPATH/patchelf step.
3. The applicable upstream copyright and license notices for every shipped component, preserved in the product and the fulfillment bundle. For Qt, map every deployed module/plugin to its own source package, attributions and license election; do not apply one blanket Qt license label.
4. The complete corresponding source required by each applicable license, including modifications and scripts needed to control compilation and installation where required. Build instructions/toolchain details help establish technical provenance and support rebuilding, but exact toolchain/container digests and bit-for-bit reproducibility are not blanket legal prerequisites. For libraries subject to relinking/replacement terms, demonstrate the actual permitted replacement mechanism and assess whether installation information applies to the conveyed product.
5. A source delivery path that remains available for the distribution's required period and is bound to the specific binary release by immutable digests. Check source-availability obligations and delivery terms against the actual selected license text; do not treat a general link to upstream or a binary SDK as corresponding source.

The retained Qt and mpv source archives, recipe files, and final payload inventories do not complete the corresponding-source bundle for either platform. Windows still needs the exact linked FFmpeg/dependency sources, patches, linked license closure, and matching Qt/MinGW source/build and replacement fulfillment. Linux still needs the exact private-library source trees and per-component notices, matching asset-to-source evidence for its mutable dependency inputs, Qt/ICU source/build correspondence, and the final-to-original member crosswalk. Do not clear either platform's readiness blocker until the specific artifact and fulfillment evidence is retained and reviewed.

The distributor-controlled mechanism identified here is a release-specific companion source archive attached to the same versioned release as each binary package, with an immutable digest and retention under distributor control. It is supported by actual retained Qt/mpv source and recipe materials, but cannot yet contain the complete corresponding source and notices for the supplied runtimes, so it is not an active compliant source offer. The conservative alternative is to withhold these binary packages until the missing runtime source/license materials are recovered or the runtime is rebuilt with a complete, controlled source and notice closure while preserving the intended portable playback feature set. Do not silently substitute host libraries, disable bundled playback, or claim readiness.
